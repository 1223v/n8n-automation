## 섹션 0. 타이틀·발표자·목차 (1분)

### 1장 · 잔말말고 n8n 오케스트레이션으로 (25초)

안녕하세요. 오늘 주제는 “잔말말고 n8n 오케스트레이션으로”입니다.

팀원들에게 제가 한 말은 하나였어요. “명령어 하나 입력하고, 하고 싶은 일만 적어 주세요.” 빠진 조건은 AI가 물어보면서 채웁니다.

오늘은 그 뒤에 숨은 설계를, 시뮬레이션 데모와 함께 보여드리겠습니다.

> 발표자 참고: 제목 아래에 “30분 · 데모는 시뮬레이션” 표기가 있습니다. 배경의 흐린 글자는 킷의 7단계 이름입니다.

### 2장 · 발표자 (15초)

저는 차량제어서비스개발팀 조현식 책임입니다. 팀 배포 캘린더, ITOM EOS 현황, Jira 납기 알림 같은 반복 작업을 공용 PC의 n8n으로 24시간 돌리고 있습니다.

> 발표자 참고: 화면에는 배포 후 시뮬레이터 E2E 리포트까지 네 가지가 있습니다. 다 읽지 않습니다.

### 3장 · 오늘의 흐름 (20초)

흐름은 이렇습니다. 먼저 자동화를 만들 때 겪은 문제와, 그래서 세운 원칙을 봅니다. 그다음 AI에게 일을 어떻게 나누고 어떻게 검증하게 했는지 내부 설계를 설명하고, 설치와 데모, 실제 활용 순서로 마무리하겠습니다.

## 섹션 1. 문제 (2분 25초)

### 4장 · 자동화 하나 만들려는데, 거쳐야 할 일이 너무 많습니다 (25초)

n8n 워크플로우는 노드를 선으로 이어 만드는 자동화 흐름입니다.

그런데 하나 만들려면 노드를 찾고, 설정해서 잇고, Claude에게 수정을 부탁하고, 실행하고, 또 고치고, 배포까지 해야 하죠. (가리키기: 카드 01~06)

자동화하려고 시작했는데 만드는 과정부터 부담이 되니, 결국 익숙한 수작업으로 돌아가게 됩니다.

### 5장 · 「이렇게 고쳐줘」 한 마디의 결말 (30초)

특히 세 번째, Claude에게 수정을 부탁하는 단계에서 이런 일이 있었습니다.

“이렇게 고쳐줘” 한 마디를 던지고 잠깐 자리를 비웠는데, 돌아와 보니 워크플로우가 제 말과 다르게 이미 바뀌어 있더라고요.

[PAUSE]

[청중] 비슷한 경험 있으신 분, 손 한번 들어 주시겠어요? 네, 저만 그런 게 아니었네요.

### 6장 · 다섯 가지 반복되는 문제 (60초)

정리해 보니 같은 문제가 다섯 가지로 반복됐습니다.

[→ 카드 1 · 요구사항 오해] 첫째, 요구사항 오해. “알림 추가해줘” 했더니 확인 한 번 없이 엉뚱한 조건에 알림이 붙어 있습니다.

[→ 카드 2 · 구식 문법] 둘째, 구식 문법. AI가 기억에 의존하다 보니 예전 노드 파라미터나 오래된 typeVersion을 씁니다. 실행해 봐야 그제야 깨지죠.

[→ 카드 3 · 무검증] 셋째, 무검증. UI에서 손으로 고쳐도, AI가 고쳐도 검증을 따로 안 부르면 실수가 그대로 넘어갑니다.

[→ 카드 4 · 무기록] 넷째, 무기록. 무엇을 왜 바꿨는지 남지 않아서, 일주일 뒤엔 “이거 누가 왜 바꿨지?”가 됩니다.

[→ 카드 5 · 셋업 삽질] 다섯째, 셋업 삽질. “n8n 설치 어떻게 했더라, 스크립트 어디 있지?” 게다가 스크립트엔 제 PC 절대 경로가 박혀 있어서 다른 PC에선 돌지도 않았습니다.

> 발표자 참고: 진입하면 제목만 보입니다. 카드 다섯 장이 다 나온 뒤 한 번 더 누르면 7장입니다. ←는 카드를 하나씩 되돌립니다.

### 7장 · 결국, 나만 만들고 나만 수정할 수 있는 워크플로우가 됩니다 (30초)

이게 반복되면 결국 나만 만들고, 나만 고칠 수 있는 워크플로우가 됩니다.

설정 방법도, 고친 이유도, 확인 기준도 제 머릿속에만 있으니 파일을 공유해도 문제가 생기면 결국 저를 찾게 되죠.

[PAUSE]

편해지려고 자동화했는데, 오히려 제가 관리할 일만 늘어난 겁니다. 그래서 만드는 부담과 관리하는 부담을 같이 줄이려고, 세 가지 원칙을 세웠습니다.

## 섹션 2. 제작 원칙과 쉬운 사용 경험 (1분 45초)

### 8장 · 그래서 제가 세운 원칙은 세 가지입니다 (25초)

첫째, 세팅이 쉬워야 합니다. 시작부터 지치면 다시 안 쓰거든요.

둘째, 노드 사용법이나 연결을 몰라도 편하게 만들 수 있어야 합니다.

셋째, 만든 사람이 아니어도 누구나 이해하고 고칠 수 있어야 합니다.

이 원칙을 담은 진입점이 바로 Claude 대화창 하나였습니다.

### 9장 · 대화 하나로, 자동화를 만듭니다 (60초)

(진입하면 명령어와 요청이 자동으로 타이핑됩니다)

설치와 설정을 마쳤다면, 명령어 하나와 하고 싶은 일 한 줄이면 됩니다. “매일 아침 배포 캘린더를 갱신하고 팀 채널에 알려줘.”

(입력창이 사라지고 1단계 분석이 자동으로 재생됩니다)

먼저 파일을 읽고, 데이터가 어디서 어디로 흐르는지 파악합니다.

[→ 2 요건 명확화] 그리고 제가 말하지 않은 것, 몇 시에 돌지, 어디로 알릴지, 실패하면 어떻게 할지를 먼저 묻습니다.

[→ 3 요건 확인] 이해한 걸 요약하고, 사람이 맞다고 해야 넘어갑니다.

[→ 4 리서치] 기억 대신 공식 문서와 기존 구현에서 근거를 찾고,

[→ 5 계획 수립] 계획을 파일로 남긴 뒤, 여기서 한 번 더 사람이 승인합니다.

[→ 6 실행] 승인한 범위만 구성·연결하고, 필수 데이터와 실패 분기까지 검증합니다.

[→ 7 보고] 이 모든 과정이 _workspace_n8n 폴더에 기록으로 남습니다. 그래서 만든 사람이 아니어도 기록을 읽고 이어서 고칠 수 있죠.

> 발표자 참고: 장면이 움직이는 중에 누르면 그 장면이 바로 완성되고, 한 번 더 눌러야 다음 단계로 갑니다. 타이핑 중에 누르면 1단계 완성 화면으로 건너뜁니다. 7단계 다음 입력은 10장입니다. 화면의 질문·답변·승인은 설명용 예시입니다.

## 섹션 3. 어떻게 사고하나 (3분)

### 11장 · 역할 이름보다 작업의 의존관계를 먼저 그린다 (60초)

여기부터는 내부 설계입니다. 공개 스킬인 harness의 설계 기법을 배포 캘린더에 적용한 설계입니다.

(가리키기: 흐름도)

역할부터 늘리면 작은 일에도 큰 팀이 붙거든요. 그래서 저는 일의 순서부터 그립니다. 현재 JSON을 알아야 계획을 세우고, 바꾼 게 있어야 검증을 하죠. 반면 노드 공식 사양 조사와 기존 구현 조사는 서로 기다릴 필요가 없습니다.

[→ 순차] 분석, 계획, 구현, 검증은 순서대로 갑니다.

[→ 병렬] 독립된 조사만 동시에 돌리고요. 결과만 받으면 되니까 서브에이전트로 충분하다고 봤습니다. 서로 협의가 필요했다면 에이전트 팀을 골랐을 겁니다.

[→ 역할 분리 · 정리 문장] 그리고 만드는 역할과 판정하는 역할을 나눕니다. 빠르게 하려는 게 아니라, 다른 눈으로 보려는 거죠. 에이전트 수는 이렇게 일의 관계를 그린 다음에 정합니다.

> 발표자 참고: 11~18장은 revfactory/harness 기법을 배포 캘린더에 적용한 설계입니다. harness 원문은 에이전트 팀을 기본으로 두고, 에이전트끼리 통신이 필요 없으면 서브에이전트도 가능하다고 봅니다. 서브에이전트 선택은 이 설계의 판단입니다.

### 12장 · 각 에이전트가 알아야 할 것만 전달한다 (60초)

그럼 각 역할에 무엇을 넘길까요? 전부 주면 나눈 의미가 줄어듭니다.

(1/6 오케스트레이터) 오케스트레이터는 요청 유형과 분기 규칙, 현재 단계와 사람 확인 여부로 다음 일을 정합니다.

[→ 2/6 빌더] 빌더는 대상 JSON, 승인된 계획, 이번에 쓸 노드 사양만 받습니다.

[→ 3/6 검증자] 검증자는 기대 결과, 실제 산출물, 샘플 입출력을 받습니다. 빌더의 “잘 됐다”는 요약만 보고 판정하면 안 되니까요.

[→ 4/6 필요한 만큼 읽기] 필요한 만큼만 읽습니다. description으로 스킬을 고르고, SKILL.md로 절차를 보고, 필요한 references만 엽니다.

[→ 5/6 설명 요청] “n8n의 IF 노드가 뭐야?”는 설명만 하고, 변경 절차는 시작하지 않습니다.

[→ 6/6 변경 요청] “이 흐름에 IF 분기를 추가해줘”는 실제 변경이라 분석, 계획, 검증을 거칩니다. 키워드가 같아도 의도가 달라서, 이런 비슷한 요청도 트리거 테스트에 넣습니다.

> 발표자 참고: 장면당 약 10초입니다. 뒤로 들어오면 6장면부터 보입니다. 근거는 harness 스킬 작성·테스트 가이드(Progressive Disclosure, 비슷하지만 트리거하면 안 되는 요청 테스트)입니다.

### 13장 · 다음 요청에서 이어 쓸 산출물까지 설계한다 (60초)

(진입하면 후속 요청이 자동으로 입력됩니다)

역할마다 결과를 파일로 남기면, 다음 요청이 그 기록을 이어 씁니다. 며칠 뒤 “알림 문구만 짧게 바꿔줘”라는 요청이 왔다고 해 볼게요.

(1 지난 요청의 맥락 읽기 · 자동 재생)

알림 노드 하나 고치는 건 순정 Claude도 하죠. 그런데 n8n에는 현재 상태만 남지, 만든 이유와 검증 내용은 안 남거든요. 그래서 지난 기록부터 읽습니다. (가리키기: 요청 → 계획 → 변경안 → 검증)

[→ 2 변경 범위 정하기] 고칠 곳은 알림 메시지 노드뿐, 조회·변환·업로드는 그대로 둡니다. 실패를 성공으로 알리지 않는다는 지난 완료 조건도 지키고요.

[→ 3 영향받는 곳 재검증] 문구만 바꿔도 메시지가 쓰는 데이터와 성공·실패 분기는 다시 봅니다. 작은 수정일수록 건너뛰기 쉬워서 절차로 넣었습니다.

[→ 4 기록 이어 쓰기] 결과는 다시 기록에 더합니다. 순정은 지금 상태만 보고 고치고, 이 킷은 왜 만들었고 무엇을 검증했는지까지 읽고 고칩니다.

> 발표자 참고: 화면의 파일명은 적용 예시입니다. 근거는 harness 오케스트레이터 템플릿의 Phase 0(작업 폴더가 있으면 이전 산출물을 읽고 필요한 부분만 다시 실행)입니다.

## 섹션 4. 어떻게 검증하나 (6분 15초)

### 14장 · 계획 승인 뒤에도, 완료 판정은 만든 쪽에 맡기지 않는다 (80초)

이제 검증입니다. Plan 모드와 비교해 볼게요. (가리키기: Plan 모드 행)

Plan 모드도 파일은 건드리지 않고 조사해서 계획을 세운 뒤, 사용자 승인을 받습니다. 여기까지는 이 킷과 같죠. 차이는 그다음입니다. 승인하면 같은 Claude가 구현하고, 끝났는지도 스스로 판단해 “완료했습니다”라고 하죠.

[→ 이 설계 행] 이 설계는 승인 뒤를 나눕니다. 빌더는 변경 도구로 만들고, 검증자는 읽기와 검사 도구로 완료 조건과 실제 산출물을 비교합니다. 결과는 통과·실패·미검증을 근거와 함께 돌려주고요. 실패하면 오류 보고서를 받은 빌더가 고치고 다시 검증하는데, 끝없이 돌지 않게 최대 두 번까지만 합니다.

단, 검증자가 고치지 못하게 하려면 도구 설정으로 막아야 합니다. 지시문에 “수정 금지”라고 쓰는 것만으로는 안 막히거든요.

[→ 완료 판정 강조] 그러니까 차이는 계획이 아니라, 승인 뒤에 누가 무엇으로 완료를 판정하느냐입니다. 참고로 지금 킷은 빌더가 validate로 직접 검사하고, 검증자 분리는 적용 설계입니다.

> 발표자 참고: 공식 문서상 Plan 모드는 계획을 승인하면 plan 모드를 빠져나와 같은 세션이 편집을 시작합니다. “최대 2회”는 harness 생성-검증 패턴의 재시도 상한 권고(2~3회) 안에서 정한 값입니다.

여기서부터 네 장은 같은 조건으로 비교합니다. 순정 Plan 모드도 n8n-mcp를 붙이면 validate, autofix, test 도구를 똑같이 쓸 수 있거든요. 그러니까 차이는 도구가 아니라 절차입니다.

(가리키기: Plan 모드 + n8n-mcp 줄) Plan 모드에는 무엇을 검사할지 정해 둔 규칙이 없어서, validate만 통과하면 끝났다고 보기 쉽습니다.

[→ 이 설계 줄] 이 설계는 샘플 입력을 넣어서, 앞 노드가 내보낸 값과 뒤 노드가 기대하는 값을 같이 봅니다.

[→ 본문] 오른쪽은 실제 pipeline.json의 결과 정규화 코드이고, 왼쪽은 필드를 일부러 뺀 테스트 입력입니다. 실제 장애 로그는 아니고요.

(가리키기: 왼쪽 입력) 앞 노드는 status success, 종료 코드 0을 줬습니다.

[청중] 종료 코드가 0이면 성공일까요?

[PAUSE]

그런데 승인일 미기재 건수, approvalDateMissingCount가 없습니다. (가리키기: 오른쪽 코드) 뒤 노드는 이 값을 0으로 채우지 않고 null로 둡니다. 필수 건수가 없으니 정상이라는 주장을 받아들이지 않고, calendarStatus를 failed로 돌려주죠.

실제 성공 메시지도 모르는 건수는 0건이 아니라 “확인 불가”로 표시합니다. 구조 검사만으로는 이런 문제를 못 잡아요. “문제 없음”과 “확인 못 함”은 다르니까요.

그럼 이 검사는 전체 검증에서 어디쯤 있을까요?

> 발표자 참고: 코드 근거는 pipeline.json의 ‘01 XML 결과 정규화’(countOrNull, 필수 건수 누락 시 failed)와 ‘성공 메시지 준비’(모르는 건수는 ‘확인 불가’)입니다. 왼쪽 JSON은 설명용 테스트 입력입니다.

(가리키기: Plan 모드 + n8n-mcp 줄) Plan 모드에서는 무엇을 어디까지 검사할지 매번 Claude가 판단합니다. test 도구가 있어도, 언제 어떤 입력으로 돌릴지는 정해져 있지 않죠.

[→ 이 설계 줄] 이 설계는 세 층을 순서대로 거칩니다.

[→ 본문] 1층은 구조와 설정입니다. 노드 설정, 표현식, 연결 참조처럼 validate가 잘하는 영역이죠.

2층은 연결 구간입니다. 샘플 데이터가 다음 노드의 기대를 채우는지 봅니다. 방금 본 필수 건수 누락이 여기서 잡힙니다.

3층은 전체 흐름입니다. 중간에 실패했는데 성공 알림 경로를 타지 않는지 끝까지 확인합니다. 외부 전송은 테스트용 채널과 저장소로 확인하고요.

(가리키기: 조회·변환 → 검사 통과 → 업로드·알림) 구간마다 확인하고, 마지막에 전체 결과를 다시 확인하는 거죠.

autofix는 표현식 형식이나 typeVersion 같은 설정 오류를 고치는 도구입니다. 빠진 데이터의 의미까지 고쳐 주진 않아요. 그건 빌더가 원인을 찾아서 고칩니다.

> 발표자 참고: autofix 수정 유형은 n8n-mcp 문서 기준(표현식 = 접두사, typeVersion, 오류 출력 설정, 노드 타입, webhook 경로 등)입니다. 구간마다 바로 검증하는 방식은 harness QA 가이드의 권장 패턴입니다.

### 17장 · “다시 고쳐” 대신 수정 가능한 오류를 돌려준다 (65초)

실패를 찾으면 돌려줘야죠. (가리키기: Plan 모드 + n8n-mcp 줄) Plan 모드에서는 에러 문구나 “다시 고쳐” 한마디를 보고, Claude가 원인을 추측해서 고칩니다.

[→ 이 설계 줄] 이 설계는 오류 보고서 형식을 고정합니다. 위치, 기대값, 실제값, 근거, 수정 대상. 다섯 칸입니다.

[→ 본문] 방금 사례로 채워 보면, 위치는 XML 결과 정규화 노드. 기대값은 음수가 아닌 정수. 실제값은 필드가 없어서 null. 근거는 누락 샘플의 데이터 계약 불충족. 수정 대상은 앞 노드 결과나 필드 매핑입니다.

(가리키기: 오른쪽 수정 지시) 여기서 중요한 건, null을 0으로 바꿔서 통과시키면 안 된다는 겁니다. 검증자는 원인을 단정하지 않고 확인할 곳을 짚어 주고, 빌더는 그 범위만 고친 뒤 정상 샘플과 누락 샘플을 둘 다 다시 돌립니다.

화면은 형식 예시입니다. 위치와 기대값, 실제값, 근거가 있어야 고칠 범위가 좁아지죠.

### 18장 · 결과물과 킷을 서로 다른 루프로 개선한다 (70초)

마지막은 개선입니다. (가리키기: Plan 모드 + n8n-mcp 줄) 순정에서도 CLAUDE.md나, 기본으로 켜진 자동 메모리로 교훈이 다음 세션에 넘어갈 수 있습니다. 그런데 자동 메모리는 무엇을 남길지 Claude가 판단하고, 이 PC에만 저장됩니다. 팀에 반영하려면 CLAUDE.md 정리를 따로 챙겨야 하죠.
