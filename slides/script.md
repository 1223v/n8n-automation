## 섹션 1. 문제 (2분 25초)

### 4장 · 자동화 하나 만들려는데, 거쳐야 할 일이 너무 많습니다 (25초)

n8n 워크플로우는 노드를 선으로 이어 만드는 자동화 흐름입니다.

그런데 하나 만들려면 노드를 찾고, 설정해서 잇고, Claude에게 수정을 부탁하고, 실행하고, 또 고치고, 배포까지 해야 하죠. 자동화하려고 시작했는데 만드는 과정부터 부담이 되니, 결국 익숙한 수작업으로 돌아가게 됩니다.

### 5장 · 「이렇게 고쳐줘」 한 마디의 결말 (30초)

특히 세 번째, Claude에게 수정을 부탁하는 단계에서 이런 일이 있었습니다.

“이렇게 고쳐줘” 한 마디를 던지고 잠깐 자리를 비웠는데, 돌아와 보니 워크플로우가 제 말과 다르게 이미 바뀌어 있더라고요.

### 6장 · 다섯 가지 반복되는 문제 (60초)

정리해 보니 같은 문제가 다섯 가지로 반복됐습니다.

[카드 1 · 요구사항 오해] 첫째, 요구사항 오해. “알림 추가해줘” 했더니 확인 한 번 없이 엉뚱한 조건에 알림이 붙어 있습니다.

[카드 2 · 구식 문법] 둘째, 구식 문법. AI가 기억에 의존하다 보니 예전 노드 파라미터나 오래된 typeVersion을 씁니다. 실행해 봐야 그제야 깨지죠.

[카드 3 · 무검증] 셋째, 무검증. UI에서 손으로 고쳐도, AI가 고쳐도 검증을 따로 안 부르면 실수가 그대로 넘어갑니다.

[카드 4 · 무기록] 넷째, 무기록. 무엇을 왜 바꿨는지 남지 않아서, 일주일 뒤엔 “이거 누가 왜 바꿨지?”가 됩니다.

[카드 5 · 셋업 삽질] 다섯째, 셋업 삽질. “n8n 설치 어떻게 했더라, 스크립트 어디 있지?” 게다가 스크립트엔 제 PC 절대 경로가 박혀 있어서 다른 PC에선 돌지도 않았습니다.

### 7장 · 결국, 나만 만들고 나만 수정할 수 있는 워크플로우가 됩니다 (30초)

이게 반복되면 결국 나만 만들고, 나만 고칠 수 있는 워크플로우가 됩니다.

설정 방법도, 고친 이유도, 확인 기준도 제 머릿속에만 있으니 파일을 공유해도 문제가 생기면 결국 저를 찾게 되죠.

[PAUSE]

편해지려고 자동화했는데, 오히려 제가 관리할 일만 늘어난 겁니다. 그래서 만드는 부담과 관리하는 부담을 같이 줄이려고, 세 가지 원칙을 세웠습니다.

## 섹션 3. 어떻게 사고하나 (3분)

### 11장 · 역할 이름보다 작업의 의존관계를 먼저 그린다 (60초)

여기부터는 내부 설계입니다. 공개 스킬인 harness의 설계 기법을 배포 캘린더에 적용한 설계입니다.

역할부터 늘리면 작은 일에도 큰 팀이 붙거든요. 그래서 저는 일의 순서부터 그립니다. 현재 JSON을 알아야 계획을 세우고, 바꾼 게 있어야 검증을 하죠. 반면 노드 공식 사양 조사와 기존 구현 조사는 서로 기다릴 필요가 없습니다.

[순차] 분석, 계획, 구현, 검증은 순서대로 갑니다.

[병렬] 독립된 조사만 동시에 돌리고요. 결과만 받으면 되니까 서브에이전트로 충분하다고 봤습니다. 서로 협의가 필요했다면 에이전트 팀을 골랐을 겁니다.

[역할 분리 · 정리 문장] 그리고 만드는 역할과 판정하는 역할을 나눕니다. 빠르게 하려는 게 아니라, 다른 눈으로 보려는 거죠. 에이전트 수는 이렇게 일의 관계를 그린 다음에 정합니다.

### 12장 · 각 에이전트가 알아야 할 것만 전달한다 (60초)

[진입 · 1/6 오케스트레이터]

[→ 한 번 · 3/6 오른쪽: 변경 요청]

[→ 한 번 · 4/6 아래 왼쪽: 빌더]
빌더는 대상 JSON, 승인된 계획, 필요한 노드 사양을 받아 구현합니다.

## 섹션 4. 어떻게 검증하나 (5분 5초)

### 14장 · 계획 승인 뒤에도, 완료 판정은 만든 쪽에 맡기지 않는다 (80초)

이제 검증입니다. Plan 모드와 비교해 볼게요. Plan 모드도 파일은 건드리지 않고 조사해서 계획을 세운 뒤, 사용자 승인을 받습니다. 여기까지는 이 킷과 같죠. 차이는 그다음입니다. 승인하면 같은 Claude가 구현하고, 끝났는지도 스스로 판단해 “완료했습니다”라고 하죠.

[→ 이 설계 행] 이 설계는 승인 뒤를 나눕니다. 빌더는 변경 도구로 만들고, 검증자는 읽기와 검사 도구로 완료 조건과 실제 산출물을 비교합니다. 결과는 통과·실패·미검증을 근거와 함께 돌려주고요. 실패하면 오류 보고서를 받은 빌더가 고치고 다시 검증하는데, 끝없이 돌지 않게 최대 두 번까지만 합니다.

단, 검증자가 고치지 못하게 하려면 도구 설정으로 막아야 합니다. 지시문에 “수정 금지”라고 쓰는 것만으로는 안 막히거든요.

[→ 완료 판정 강조] 그러니까 차이는 계획이 아니라, 승인 뒤에 누가 무엇으로 완료를 판정하느냐입니다. 지금 킷은 빌더가 validate로 직접 검사하고, 검증자 분리는 적용 설계입니다.

### 15장 · 노드가 있는지보다, 연결 양쪽의 데이터가 맞는지 본다 (90초)

여기서부터 세 장은 같은 조건으로 비교합니다. 순정 Plan 모드도 n8n-mcp를 붙이면 validate, autofix, test 도구를 똑같이 쓸 수 있거든요. 그러니까 차이는 도구가 아니라 절차입니다.

Plan 모드에는 무엇을 검사할지 정해 둔 규칙이 없어서, validate만 통과하면 끝났다고 보기 쉽습니다.

[→ 이 설계 줄] 이 설계는 샘플 입력을 넣어서, 앞 노드가 내보낸 값과 뒤 노드가 기대하는 값을 같이 봅니다.

[→ 본문] 쉬운 예로 볼게요. 매일 아침 서버 점검 결과를 알림으로 보내는 워크플로우입니다. 왼쪽은 오류 건수, errorCount를 일부러 뺀 테스트 입력이에요. 점검 실행 자체는 success로 왔습니다.

뒤 노드가 이 빈칸을 0건으로 채우면 “오류 0건, 정상” 알림이 나갑니다. 구조는 멀쩡하니까 validate로는 못 잡죠.

오른쪽 코드는 빈칸을 0건으로 채우지 않고 모르는 값으로 둡니다. 그리고 “오류 건수 확인 못 함”으로 실패를 알리죠. 실제 배포 캘린더 파이프라인도 빠진 점검 건수를 이렇게 실패로 처리합니다.

“오류 없음”과 “확인 못 함”은 다르니까요. 이렇게 찾은 문제는 고칠 수 있도록 보고서로 정리합니다.

### 16장 · “다시 고쳐” 대신 어디가 틀렸는지 알려준다 (65초)

이 내용을 바탕으로 수정 요청은 이렇게 씁니다. “성공·실패 알림 분기를 확인하고, 두 경우를 다시 테스트하세요.”

원인이 어느 조건이나 연결에 있는지는 빌더가 확인합니다. 알림 문구만 바꿔서 끝내는 게 아니라, 실제 성공했을 때와 실패했을 때 각각 맞는 알림이 나오는지 확인하는 겁니다.

이렇게 관찰한 결과를 구체적으로 전달하면, 고칠 범위와 다시 검사할 기준이 분명해집니다.

### 17장 · 결과물과 킷을 서로 다른 루프로 개선한다 (70초)

[→ 이 설계 줄] 이 설계는 루프를 둘로 나눕니다.

[→ 본문] 왼쪽은 이번 워크플로우를 고치는 루프입니다. 생성, 검증, 부분 수정을 하고, 완료 조건을 채우거나 수정 상한에 닿으면 멈춥니다.

| autofix가 누락 데이터도 고치나요? | 아닙니다. 표현식 `=` 접두사, typeVersion, 오류 출력 설정, 노드 타입, webhook 경로 같은 설정 오류를 고칩니다. 데이터 의미는 빌더가 원인을 찾아 고칩니다. |
| 왜 최대 두 번인가요? | 무한 반복을 막기 위해서입니다. harness 생성-검증 패턴의 재시도 상한 권고(2~3회) 안에서 정했습니다. 외부 업로드나 전송을 두 번 다시 실행한다는 뜻은 아닙니다. |
| 검증자가 틀리면요? | 틀릴 수 있습니다. 실제 입력·출력과 근거를 남기고, 기계적으로 검사할 수 있는 조건은 코드로 돌립니다. 정상 사례를 막지 않는지도 같이 비교합니다. |
| 자동 메모리가 있는데 굳이 루프를 나눠야 하나요? | 자동 메모리는 기본으로 켜져 있지만, 무엇을 남길지 Claude가 판단하고 그 PC에만 저장되며, 코드에서 알 수 있는 내용은 저장하지 않습니다. 팀 전체가 쓰는 절차와 검사는 스킬·검사 코드로 고치고 같은 입력으로 비교합니다. |
| n8n 2.0에서 Execute Command가 안 보여요 | 2.0부터 기본 차단입니다. `NODES_EXCLUDE`에서 빼야 합니다(`"[]"`는 전부 허용이라 보안 위험을 따져야 함). 파일 노드는 `N8N_RESTRICT_FILE_ACCESS_TO`(기본 `~/.n8n-files`)에 결과 폴더를 넣어야 합니다. |
| npm으로 n8n을 띄우는 방식은 계속 쓸 수 있나요? | 공식 문서상 npm 설치는 n8n 3.0부터 deprecated이고, 요구 Node.js는 20.19~24.x입니다. 공용 PC 운영 방식은 발표 전에 확인합니다. |
| 토큰이 얼마나 줄었나요? | 실측 전이라 절감률은 말하지 않습니다. 첫 요청은 더 쓰고, 검증 통과까지의 총 토큰과 수정 요청 수로 비교해야 합니다. |
| 파이프라인이 매번 AI를 부르나요? | 배포 캘린더 파이프라인에는 AI 노드가 없습니다. 스크립트 실행, Code, If, HTTP Request로 돕니다. AI는 파이프라인을 만드는 과정에서 씁니다. |
