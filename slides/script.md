11~19장은 `revfactory/harness`의 기법을 배포 캘린더에 적용한 설계다. 원본의 Markdown 지침·템플릿과 실제 코드 검사를 구분한다. 별도 검증자, 파일 전달 계약, 최대 2회 수정, 비교 평가 표는 적용 예시다. 15장의 정규화·메시지 처리 로직은 로컬 코드에서 확인했다. 실행 로그나 개선 수치는 만들어 넣지 않는다.

## 시간 조절

- **30분:** 위 배분대로 진행. 11~13장은 각 60초, 14~19장은 80·90·70·65·65·70초.
- **20분:** 소개 1분 + 문제 2분 25초 + 사용 경험 1분 35초 + 설계 사고 2분 15초 + 구현 5분 + 데모 3분 + 활용·차별점 2분 + 마무리 1분 + 전환 여유 1분 45초. 별도 Q&A 시간은 포함하지 않는다.
- 축약판은 4장과 8~10장을 각각 25·25·55·15초, 11~13장을 각 45초, 14~19장을 55·65·50·45·45·40초로 줄인다. 데모는 멈춤 컷 위주로 설명하고, 실전 활용은 23장만 40초로 설명한다. 24·25장의 핵심은 대본 참고로 남긴다.

## 강조할 핵심 메시지

1. 세팅이 쉽고 편하게 만들며, 만든 워크플로우는 누구나 이어서 수정할 수 있어야 한다.
2. 쉬운 진입점 뒤에는 검증 가능한 완료 조건이 있다.
3. 역할 수보다 의존관계, 전달할 정보, 산출물을 먼저 설계한다.
4. 빌더와 검증자를 나누고 연결된 앞 노드 출력·뒤 노드 입력 양쪽을 비교한다.
5. 실패 근거를 수정 가능한 형태로 전달하고 재검증한다. 미검증은 성공이 아니다.
6. 이번 결과물 수정과 다음 실행을 위한 킷 개선을 구분한다.

## 청중 상호작용 포인트

## 섹션 1. 문제: 번잡한 제작 과정과 AI에게 맡겼을 때 생기는 일 (2분 25초)

### 슬라이드 4 — 자동화 하나 만들려는데, 거쳐야 할 일이 너무 많습니다 (신규 · 제작 배경) [~25초]

먼저 n8n 워크플로우는 노드를 선으로 이은 자동화 흐름입니다.

하나를 만들려면 노드를 찾고, 설정하고 연결해야 합니다. 수정하고 실행해 보고, 다시 고친 뒤 배포까지 해야 합니다. 자동화하려고 시작했는데 만드는 과정부터 번잡합니다.

이러면 시간을 들이는 대신 익숙한 수작업으로 돌아가게 됩니다.

[전환] 이 번거로움을 줄여보려고 AI에게 맡겨봤습니다.

### 슬라이드 5 — "이렇게 고쳐줘" 한 마디의 결말 (원안 #3) [~30초]

그래서 AI에게 맡겨봤습니다. AI에게 "이렇게 고쳐줘" 한 마디를 던졌습니다. 잠시 뒤 돌아와 보니, 제가 말한 것과 다르게 이해한 채로 워크플로우가 이미 바뀌어 있었습니다.

### 슬라이드 6 — 다섯 가지 반복되는 문제 (원안 #4) [~60초]

> 조작: 제목만 보이는 상태로 시작한다. → / Space를 누를 때마다 카드가 하나씩 나타나고, 다섯 장이 다 나온 뒤 한 번 더 누르면 7장으로 넘어간다. ←는 카드를 하나씩 되돌린다.

이런 문제가 다섯 가지 패턴으로 반복됐습니다. 전부 제가 실제로 겪은 것들입니다. 하나씩 한 문장 상황극으로 갑니다.

[→ 카드 1] 첫째, 요구사항 오해. "알림 추가해줘" 했더니, 확인 한 번 없이 엉뚱한 조건에 알림이 붙어 있습니다.

[→ 카드 2] 둘째, 구식 문법. AI는 기억과 학습 데이터로 씁니다. 그래서 오래된 노드 파라미터, 오래된 `typeVersion`을 씁니다. 실행해 보면 그제야 깨집니다.

[→ 카드 3] 셋째, 무검증. UI에서 손으로 고치면 실수를 바로 알기 어렵습니다. AI가 고쳐도 마찬가지입니다. 검증을 따로 안 부르면 그냥 넘어갑니다.

[→ 카드 4] 넷째, 무기록. 무엇을 왜 바꿨는지 남지 않습니다. 일주일 뒤에 보면 "이거 누가 왜 바꿨지?"가 됩니다.

[→ 카드 5] 다섯째, 셋업 삽질. [청중에게 질문] "n8n 설치 어떻게 했더라", "그 스크립트 어디 있지" 매번 반복하신 분? 게다가 스크립트에는 개인 PC 절대 경로가 박혀 있어서, 다른 사람 PC에서는 그냥 안 돕니다.

[전환] 이런 문제를 매번 만든 사람이 해결하다 보면, 결국 어떤 워크플로우가 남을까요?

### 슬라이드 7 — 나만 만들고, 나만 수정할 수 있는 워크플로우 (원안 #5) [~30초]

앞에서 본 다섯 가지 문제가 반복되면, 결국 **나만 만들고 나만 수정할 수 있는 워크플로우**가 됩니다.

설정 방법, 수정한 이유, 확인 기준이 만든 사람의 기억에만 남으니, 파일을 공유해도 문제가 생길 때마다 저를 다시 찾게 됩니다.

[PAUSE] **편해지려고 자동화했는데, 오히려 제가 관리할 일만 더 늘어난 겁니다.** 자동화가 하나 늘 때마다 챙겨야 할 설정과 오류, 수정 요청도 함께 늘었습니다.

[전환] 그래서 만드는 부담과 이후의 관리 부담을 줄이고, 팀원도 함께 만들고 고칠 수 있도록 세 가지 원칙을 세웠습니다.

## 섹션 2. 제작 원칙과 쉬운 사용 경험 (1분 45초)

### 슬라이드 8 — 그래서 제가 세운 원칙은 세 가지입니다 (신규 · 제작 원칙) [~25초]

그래서 이 킷을 만들며 세운 원칙은 세 가지입니다.

세팅이 쉬워야 합니다. 시작부터 지치지 않도록요. 편하게 만들 수 있어야 합니다. 노드 사용법이나 연결을 직접 익히지 않아도 되게요. 그리고 만든 워크플로우는 누구나 수정할 수 있어야 합니다. 만든 사람의 기억에만 의존하지 않도록 변경한 이유와 확인 방법을 남겨, 다른 팀원도 이해하고 이어서 고칠 수 있어야 합니다.

팀원도 쉽게 시작하도록 오케스트레이션을 `n8n-automation` 플러그인으로 묶었습니다. 이 원칙을 담은 진입점이 Claude 대화창 하나였습니다.

### 슬라이드 9 — 대화 하나로, 자동화를 만듭니다 (원안 #11·#8 통합) [~60초]

[큰 대화창 · 타이핑, 약 6초] 플러그인 설치와 환경·연결 설정을 마쳤다면 `/n8n-automation:n8n-workflow-manager`와 “매일 아침 배포 캘린더를 갱신하고 팀 채널에 알려줘”를 입력합니다. 입력이 끝나면 대화창 전체가 위로 빠져나가 사라집니다.

화면은 큰 박스 하나에 단계 이름과 핵심 동작만 보여줍니다. 질문·답변과 작업 장면은 한 번에 하나씩 교체하며 누적하지 않습니다. 각 단계는 약 6초 동안 동작한 뒤 멈추고, 발표자가 다음 입력으로 넘깁니다. 세부 내용은 아래 대본으로 설명하며 전체 약 60초를 유지합니다.

1. **분석:** 파일을 읽고, 입력 → 변환 → 출력 구조를 정리합니다. 스크립트의 XML·HTML·업로드 단계와 워크플로우의 데이터 흐름을 확인합니다.
2. **요건 명확화:** 언제 실행할지, Teams에 어떤 결과를 알릴지, 실패하면 어떻게 할지 질문하고 답을 받습니다. 매일 08:00 KST와 수동 실행, 점검 건수 3종과 업로드 결과, 오류 알림 후 실패 종료라는 조건입니다.
3. **요건 확인:** 이해한 요건을 요약합니다. 화면의 확인 응답은 사람의 응답 예시이며, AI가 스스로 승인하는 것이 아닙니다.
4. **리서치:** 공식 문서와 기존 구현에서 실행 조건과 검증 기준을 찾습니다. 기억에 의존하지 않고 설정할 내용과 확인할 내용을 구분합니다.
5. **계획 수립:** 구성 → 연결 → 검증 순서를 `_workspace_n8n/`에 파일로 남깁니다. 실행 전에 사람이 계획을 승인하는 두 번째 지점입니다.
6. **실행:** 승인 범위의 노드를 구성하고 연결합니다. 화면은 구성 → 연결 → 검증 세 동작으로 단순화했습니다. 구조, 필수 데이터, 실패 시 성공 알림 차단을 샘플로 확인하는 과정을 보여줍니다.
7. **보고:** 킷은 각 단계의 분석·요건·계획·실행·검증 결과를 `_workspace_n8n/`에 기록합니다. 보고 단계에서는 누적된 작업 기록과 남은 운영 확인 사항을 정리합니다. 무엇을 왜 바꿨고 어떻게 확인했는지 남기므로, 만든 사람이 아니어도 기록을 읽고 같은 대화에서 이어서 수정을 요청할 수 있습니다.

[전환] 이 가운데 사람이 확인하는 두 지점을 보겠습니다.

> 조작: 진입 시 타이핑 → 대화창 완전 퇴장 → 분석 장면까지 자동 재생됩니다. 이후 각 단계는 발표자가 넘깁니다. → / Space / PageDown / 다음 버튼은 진행 중인 장면을 즉시 완성하고, 다시 입력하면 다음 단계로 이동합니다. 보고가 완성된 뒤 다음 입력은 10장으로 이동합니다. 이전 입력은 이전 단계의 완성 화면, 분석에서는 완성된 요청 화면, 그다음은 8장으로 이동합니다. ‘처음부터’ 버튼은 타이핑부터 재생합니다. 10장에서 뒤로 진입하면 보고의 완성 화면입니다. 동작 줄이기 설정에서는 단계별 완성 화면을 표시하며 수동 이동은 유지합니다. 인쇄에서는 요청과 7단계 요약을 한 페이지에 표시합니다.

### 슬라이드 11 — 역할 이름보다 작업의 의존관계를 먼저 그린다 (재구성 · n8n 적용 설계) [~60초]

> 조작: 진입하면 작업 흐름도가 먼저 부드럽게 나타납니다. 화살표를 따라 빛이 이동해 진행 방향을 보여주며, 병렬 조사 두 갈래는 동시에 움직입니다. → / Space / PageDown으로 아래의 **순차 → 병렬 → 역할 분리** 박스를 하나씩 표시합니다. 세 번째 박스와 함께 정리 문장이 나타나고, 다음 입력은 12장으로 이동합니다. ← / PageUp은 박스를 하나씩 되돌립니다.

이제 내부를 어떻게 설계했는지 보겠습니다. 여기부터는 harness의 기법을 배포 캘린더에 적용한 설계입니다.

[흐름도] 역할 이름부터 늘리면 작은 작업에도 큰 팀이 붙습니다. 저는 작업의 의존관계부터 그립니다. 현재 JSON을 알아야 변경을 계획할 수 있고, 변경이 있어야 검증할 수 있으니 이 구간은 순차입니다. 반면 대상이 정해진 뒤 노드 공식 사양과 기존 구현 관례를 조사하는 일은 독립적으로 진행할 수 있습니다.

[→ 순차] 분석 결과가 있어야 계획하고 구현·검증할 수 있습니다.

[→ 병렬] 독립적인 자료 조사만 동시에 진행합니다. harness가 제시하는 파이프라인과 팬아웃/팬인을 이 관계에 맞춰 선택한 것입니다. 결과만 전달하면 되는 구간은 서브에이전트로 충분하고, 서로 협의해야 하는 작업이면 팀 통신을 검토합니다. 

[→ 역할 분리 · 정리 문장] 빌더와 검증자를 나누는 이유는 병렬 실행이 아니라 서로 다른 판단 관점을 확보하기 위해서입니다.

[전환] 역할을 나눴으면 각 역할이 어떤 정보를 받을지도 정해야 합니다.

### 슬라이드 12 — 각 에이전트가 알아야 할 것만 전달한다 (재구성 · n8n 적용 설계) [~60초]

> 화면: 한 박스가 형태와 내용을 바꾸며 6장면으로 전환됩니다. 한 장면씩 약 10초 설명합니다. → / Space / PageDown 또는 다음 버튼으로 진행하고, ← / PageUp 또는 이전 버튼으로 돌아갑니다. 6장면 다음은 13장, 1장면 이전은 11장입니다. 뒤로 진입하면 6장면을 보여줍니다. 인쇄에서는 6장면을 한 페이지에 요약합니다.

1. **오케스트레이터:** 역할만 나누고 모든 자료를 전부 주면 컨텍스트 분리 효과가 줄어듭니다. 요청 유형·분기 규칙·현재 단계·사람 확인 상태를 전달해 다음 작업을 결정하게 합니다.
2. **빌더:** 대상 JSON과 승인된 변경 계획, 이번에 사용할 노드 사양만 전달합니다.
3. **검증자:** 기대 결과·변경 산출물·샘플 입력·실제 출력을 전달합니다. 빌더가 잘했다고 쓴 요약만 읽고 완료를 판정하면 안 됩니다.
4. **필요한 만큼 읽기:** Progressive Disclosure입니다. description으로 스킬을 고르고, SKILL.md로 절차를 읽은 뒤, 이번 작업에 필요한 references만 더 읽습니다.
5. **설명 요청:** “n8n의 IF 노드가 뭐야?”는 일반 질문입니다. 설명으로 답하고 변경 파이프라인을 호출하지 않습니다.
6. **변경 요청:** “이 흐름에 IF 분기를 추가해줘”는 실제 변경입니다. 분석·계획·검증 경로를 따릅니다. 같은 키워드여도 요청 의도로 구분해야 하며, 이런 유사 요청도 트리거 테스트에 넣습니다.

[전환] 그리고 넘기는 정보는 대화 요약으로만 남기지 않습니다.

### 슬라이드 13 — 다음 에이전트가 읽을 산출물까지 설계한다 (재구성 · n8n 적용 설계) [~60초]

각 역할의 출력이 다음 역할의 입력이 되도록 파일 경로와 내용을 정합니다. 여기서 다음 에이전트는 바로 다음 단계를 맡은 역할과, 나중에 새 대화에서 이어받는 에이전트를 모두 뜻합니다. 같은 기록은 사람도 읽고 추적할 수 있습니다. 이 화면의 파일명은 적용 예시이고, 핵심은 요청, 계획, 변경안, 검증 근거가 끊기지 않는 것입니다. 이렇게 남겨야 다음 대화에서도 이전 결과를 읽고 이어갈 수 있습니다.

예를 들어 “알림 문구만 짧게”라는 요청이 왔다고 조회와 업로드까지 다시 만들 이유는 없습니다. 기존 워크플로우와 검증 결과를 읽고 메시지 구성 부분을 고칩니다. 다만 수정한 부분만 보는 것이 아니라, 메시지가 소비하는 데이터와 성공·실패 분기까지 영향을 확인합니다. 외부 업로드를 재실행하는 문제는 잠시 뒤 따로 다루겠습니다.

[전환] 이제 이 설계를 실제 생성과 검증 역할로 조립해 보겠습니다.

## 섹션 4. 어떻게 검증하나 — AI가 스스로 검증하고 고칠 수 있게 설계하는 방법 (7분 20초)

### 슬라이드 14 — 빌더에게 완료 판정까지 맡기지 않는다 (재구성 · n8n 적용 설계) [~80초]

빌더가 자기 변경을 설명하는 것과, 기대 조건을 만족했다고 판정하는 것은 다른 일입니다. 이 설계에서는 빌더와 검증자를 별도 역할로 둡니다. 빌더는 승인 계획과 현재 워크플로우를 받아 변경안을 만들고, 검증자는 완료 조건과 실제 산출물을 읽어 비교합니다.

화면의 정의는 역할 계약 예시입니다. 빌더에게는 변경 도구를, 검증자에게는 읽기와 검사 실행 도구를 배정합니다. 검증자가 읽기만 할 수 있으면 실행 가능한 검사를 못 하므로 검사 실행 권한도 필요합니다. 실제 권한 제한은 사용하는 실행 환경에 별도로 설정해야 합니다. Markdown에 “금지”라고 적는 것 자체가 권한 차단 코드는 아닙니다.

검증자는 통과·실패·미검증을 구분하고 근거를 반환합니다. 실패하면 빌더가 수정하지만, 수정했다는 답변만으로 닫지 않고 다시 검증합니다. 이것이 생성-검증 패턴을 적용한 루프입니다.

[전환] 그럼 검증자는 구체적으로 무엇을 비교할까요?

> 근거: [harness / references/agent-design-patterns.md](https://github.com/revfactory/harness/blob/cceac68ea1d0ad198ef4b7b906cd238375836387/skills/harness/references/agent-design-patterns.md).

### 슬라이드 15 — 노드가 있는지보다, 연결 양쪽의 데이터가 맞는지 본다 (재구성 · n8n 적용 설계) [~90초]

이 장은 실제 pipeline.json 안의 01 XML 결과 정규화 코드를 바탕으로 합니다. 왼쪽은 필수 필드를 일부러 뺀 테스트 입력 예시입니다. 앞 노드는 success와 종료 코드 0을 줬지만, 승인일 미기재 건수인 approvalDateMissingCount가 없습니다.

뒤 노드 코드는 해당 값을 읽고 음수가 아닌 정수인지 확인합니다. 값이 없으면 0이 아니라 null이 됩니다. 그리고 정상 실행이라고 주장한 결과에서 필수 건수가 null이면 calendarStatus를 failed로 돌려줍니다. 따라서 명령이 종료됐다는 사실과 업무 결과가 준비됐다는 사실은 다릅니다.

출력 노드와 입력 노드가 존재하는지만 검사했다면 이 문제를 놓칩니다. 앞 노드가 무엇을 내보냈는지, 뒤 노드가 무엇을 기대하는지 양쪽을 비교해야 합니다. 알림 코드도 유효한 건수는 숫자로 표시하고, 확인하지 못한 값은 “확인 불가”로 표시합니다. 왼쪽 데이터는 검사를 설명하기 위한 예시이며, 실제 장애 로그는 아닙니다.

[전환] 이 데이터 검사는 전체 검증 중 어느 위치에서 할까요?

> 근거: [harness / references/qa-agent-guide.md](https://github.com/revfactory/harness/blob/cceac68ea1d0ad198ef4b7b906cd238375836387/skills/harness/references/qa-agent-guide.md). 실제 코드 확인: `pipeline.json`의 `01 XML 결과 정규화` 및 `성공 메시지 준비`. 입력 JSON은 검사를 설명하기 위한 예시이며 운영 장애 로그가 아니다.

### 슬라이드 16 — 한 번의 검증으로 끝내지 않는다 (재구성 · n8n 적용 설계) [~70초]

검증은 세 층으로 나눕니다. 첫 번째는 구조와 설정입니다. 노드 설정, 표현식, 연결 참조가 유효한지 검사합니다. n8n 검증 도구가 맡을 수 있는 영역입니다. 두 번째는 연결 구간입니다. 샘플 데이터를 넣고 실제 값이 다음 노드가 기대하는 형태와 의미를 만족하는지 봅니다. 방금 필수 건수 누락이 여기에 해당합니다.

세 번째는 전체 흐름입니다. 정상일 때 기대한 메시지가 만들어지는지, 실패일 때 성공 알림이 선택되지 않는지 확인합니다. 조회·변환 구간을 먼저 검사하고 업로드·알림을 연결한 뒤 전체를 다시 봅니다. 외부 전송 검사는 테스트용 채널·저장소로 수행합니다.

설정이 맞다고 업무 결과까지 맞는 것은 아닙니다. autofix는 지원하는 설정 오류를 고치는 도구이고, 누락 데이터의 의미까지 판단해 모든 오류를 고쳐주는 것은 아닙니다.

[전환] 실패를 발견했다면 빌더가 고칠 수 있는 형태로 돌려줘야 합니다.

> 근거: [harness / references/qa-agent-guide.md](https://github.com/revfactory/harness/blob/cceac68ea1d0ad198ef4b7b906cd238375836387/skills/harness/references/qa-agent-guide.md).

### 슬라이드 17 — “다시 고쳐” 대신 수정 가능한 오류를 돌려준다 (재구성 · n8n 적용 설계) [~65초]

“검증 실패, 다시 고쳐”라고만 돌려주면 빌더는 다시 전체를 추측합니다. 그래서 오류 보고서의 형식을 고정합니다. 위치, 기대값, 실제값, 근거, 수정 대상입니다. 이 예시의 기대값은 음수가 아닌 정수인데 실제 입력에는 필드가 없습니다. 정규화 노드가 실패 처리한 것은 잘못이 아니라 검사가 작동한 결과입니다.

그러므로 실패를 없애겠다고 null을 0으로 바꾸면 안 됩니다. 앞 노드 결과에 데이터가 빠졌는지, 이름이 달라 전달되지 않았는지 확인해야 합니다. 검증자는 원인을 단정하지 않고 관측한 차이와 확인할 대상을 전달합니다. 빌더가 그 범위를 고친 다음 정상 입력과 누락 입력을 모두 다시 검사합니다.

화면은 보고 형식 예시이며 실제 실행 로그가 아닙니다. [전환] 이 왕복이 끝나지 않을 때도 미리 정해야 합니다.

### 슬라이드 18 — 재시도 횟수와 멈출 조건도 구현의 일부다 (재구성 · n8n 적용 설계) [~65초]

이 적용 설계에서는 초기 생성 뒤 수정 기회를 최대 두 번 둡니다. 매 수정 뒤 같은 기준으로 재검증하고, 필수 검사가 계속 실패하면 중단해 원인과 남은 작업을 보고합니다. 검사를 못 한 상태도 통과로 바꾸지 않습니다. 두 번은 이 발표에서 선택한 정책이지, 모든 상황의 정답은 아닙니다.

또 하나는 AI가 워크플로우를 수정하는 것과 외부 작업을 다시 실행하는 것을 구분하는 것입니다. 업로드 요청이 시간 초과됐다고 이미 업로드되지 않았다는 뜻은 아닙니다. 반영 여부부터 확인해야 중복 전송을 피할 수 있습니다.

harness 템플릿의 일반 에이전트 장애 재시도와 생성-검증 수정 횟수는 다른 정책입니다. 이 사례에서는 필수 검증 실패를 누락한 채 성공 결과로 진행하지 않습니다. [전환] 실행을 고치는 일과 킷 자체를 개선하는 일도 나누어 보겠습니다.

> 근거: [harness / references/orchestrator-template.md](https://github.com/revfactory/harness/blob/cceac68ea1d0ad198ef4b7b906cd238375836387/skills/harness/references/orchestrator-template.md).

### 슬라이드 19 — 결과물과 킷을 서로 다른 루프로 개선한다 (재구성 · n8n 적용 설계) [~70초]

지금 요청의 워크플로우를 고치는 루프와, 다음 요청에서 더 잘하도록 킷을 고치는 루프는 다릅니다. 앞의 루프는 빌더와 검증자가 돌고, 뒤의 루프는 반복된 실패를 보고 스킬과 검사를 개선하는 과정입니다. 같은 실패가 반복되면 단순히 프롬프트를 길게 붙이기보다, 누락된 판단 기준을 넣거나 반복 작성되는 검사를 스크립트로 묶습니다.

개선 전후에는 같은 요청과 입력으로 비교합니다. 정상 데이터, 필수 건수가 빠진 데이터, 그리고 IF 설명과 분기 추가처럼 비슷하지만 다른 요청을 사용합니다. 결과가 존재한다는 쉬운 기준만으로는 킷의 가치를 구별할 수 없습니다. 오류를 잡았는지, 정상 결과를 잘못 막지 않았는지, 시간과 재작업은 어땠는지를 함께 봅니다. 화면의 대시는 아직 측정하지 않았다는 뜻입니다.

[전환] 여기까지는 적용 설계와 검사 방법입니다. 이제 이 킷을 팀원이 어떻게 받아 쓰는지부터 보겠습니다.

### 슬라이드 20 — 한 번 설치하면, 업데이트는 알아서 따라옵니다 (원안 #35 → 이동·변경) [~45초]

[PAUSE] 이런 생각이 드실 수도 있습니다. "이거 설치해도, 어차피 업데이트할 때마다 zip 파일 풀어서 다시 넣어줘야 하는 거 아니야?"

하지만 Claude 마켓플레이스로 플러그인을 등록해 두었기 때문에, 마켓플레이스 자동 업데이트를 한 번 켜 두시면 제가 GitLab에 새 버전을 올릴 때마다 최신 버전을 쓰실 수 있습니다. [화면: ③ 명령 → 아래 흐름] 중앙에서 라이브러리처럼 관리되니, 여러분은 사용만 하시면 됩니다.

[전환] 그럼 설치부터 n8n 기동까지, 기존 킷의 동작을 재현한 시뮬레이션으로 보겠습니다. 새 검증자와 두 번 수정 정책의 실행 증거를 보여주는 데모는 아닙니다.

> 발표자 참고: 화면의 명령은 다음과 같다. 플러그인과 마켓플레이스 이름은 모두 `n8n-automation`이다.
>
> ```text
> /plugin marketplace add https://gitlab.hmc.co.kr/infoccs/service/dkc/automation/n8n-automation.git
> /plugin install n8n-automation@n8n-automation
> /plugin → Marketplaces → n8n-automation 선택 → Enable auto-update
> ```
>
> 자동 업데이트 표현의 사실 범위 — [Claude Code 공식 문서 · Configure auto-updates](https://code.claude.com/docs/en/discover-plugins#configure-auto-updates), [플러그인 마켓플레이스 문서](https://code.claude.com/docs/en/plugin-marketplaces) 기준:
>
> - 공식 Anthropic 마켓플레이스와 달리 팀 GitLab 같은 서드파티 마켓플레이스는 자동 업데이트가 **기본 꺼짐**이다. 팀원 각자가 ③으로 켜거나, 관리자가 managed settings의 `extraKnownMarketplaces` 항목에 `"autoUpdate": true`를 넣어 일괄로 켠다.
> - Claude Code는 세션 시작 후(최대 10분 임의 지연) 백그라운드에서 마켓플레이스와 설치된 플러그인을 갱신한다. 실행 중인 세션은 시작 때 불러온 버전을 쓰고, 갱신 알림 뒤 `/reload-plugins` 또는 다음 실행부터 새 버전이 적용된다. "바로바로"가 실시간 반영으로 들리지 않게 말한다.
> - `plugin.json`(또는 마켓플레이스 항목)에 `version`을 적었다면 새 버전을 올릴 때 이 값을 올려야 팀원에게 전파된다. 적지 않았다면 git 커밋 SHA가 바뀔 때마다 갱신된다. 킷 소스가 이 PC에 없어 현재 `version` 사용 여부는 확인하지 못했다.
> - 비공개 저장소를 HTTPS로 받으면 백그라운드 pull이 git credential helper를 쓰지 않아 자동 갱신이 간헐적으로 실패할 수 있다. SSH 원격이나 토큰을 넣은 `insteadOf` URL 설정으로 해결한다. 사내 GitLab 접근 방식은 발표 전 확인한다.
> - zip을 받아 압축을 풀어 배치하던 방식은 `readme.md`의 "압축 해제" 절에 남아 있는 이전 방식이다.
> - 팀 GitLab 배포 방식과 주소는 발표자가 제공한 정보다. 마켓플레이스 등록만으로 플러그인이 설치되지는 않으며, 플러그인 설치가 외부 서비스 연결 완료를 뜻하지 않는다. 실제 저장소 접근·설치·자동 갱신 실행을 검증한 화면은 아니다.

> 데모는 녹화 영상 대신 덱에 내장한 시뮬레이션이다. 화면 구성은 세 줄. 위는 **파이프라인 스테퍼**(완료 ✓ · 진행 파랑 · 사람 게이트 주황), 왼쪽은 Claude Code 터미널, 오른쪽은 그 시점의 화면(브라우저 · 산출물 파일 · n8n 캔버스). 아래 캡션에 컷 번호와 한 줄 요약, 주황 테두리와 「멈춤」 표시가 붙은 컷은 반드시 멈춰서 설명한다.

### 슬라이드 22 — 시나리오 B: "배포 캘린더 스킬을 공용 PC n8n 파이프라인으로 만들어줘" (원안 #27 → 변경) [~150초 · 컷 11개]

### 슬라이드 25 — 토큰 관점: 어디서 아끼고, 어디서 더 쓰는가 (원안 #30) [~40초]

토큰 얘기를 안 할 수 없는데, 절감률 수치가 아니라 구조로 말씀드리겠습니다.

아끼는 곳 네 가지.

첫째, 작은 작업에는 추가 질문을 붙이지 않습니다. S 등급은 현황 감사·딥 인터뷰 없이 기본 게이트만 거칩니다. 범용 오케스트레이션 플러그인이 모든 작업에 계획·검증 대화를 여는 것과 대비됩니다.

둘째, 서브에이전트 출력 격리. 분석가가 읽은 워크플로우 JSON, 리서처가 긁은 문서 본문은 서브에이전트 컨텍스트에 남고, 메인에는 요약만 돌아옵니다.

셋째, 재작업 감소. 변경 직후 validate → autofix, 3곳 교차로 최신 `typeVersion` 확인. "고쳐줘 → 깨짐 → 다시 고쳐줘" 왕복이 줄어드는 것이 총 토큰의 가장 큰 변수입니다.

넷째, 가볍게 읽기. 기존 워크플로우 확인은 후보 5개까지, 노드 구조만 읽는 structure 모드를 씁니다. 전체 JSON을 읽는 full 모드는 금지입니다.

더 쓰는 곳도 있습니다. 요건 재확인, 계획 승인, 3곳 교차 리서치, validate 호출. 그래서 첫 요청 한 번의 토큰은 순정보다 많습니다. 비교는 "검증 통과까지의 총 토큰"으로 해야 합니다.

[화면: 우측 개념 그래프 가리키며] 첫 요청 토큰은 올라가고, 검증 통과까지 총 토큰은 내려간다. 축은 비워 뒀습니다. 실측 예정입니다.

하나 더. 로컬에 설치된 범용 오케스트레이션 플러그인의 스킬 설명 37개를 합쳐 봤더니 약 5,900자, 대략 1,500토큰 추정이었습니다. 본문은 훨씬 크지만 공식 문서상 호출 시에만 로드됩니다. 그러니까 "스킬이 많아 상시 컨텍스트가 무겁다"는 토큰 수로는 작은 논점입니다. 스킬이 많을 때의 진짜 문제는 토큰 비용이 아니라, 어떤 스킬을 부를지 헷갈려 관련 없는 스킬이 잘못 호출되는 것입니다.

[전환] 마지막으로 한 문장만 남기겠습니다.
